## Settled in Phase 0

Answers from the five spikes ([spikes/](../../spikes/README.md)) and choices made during the rename.

| # | Decision | Why | Docs |
|---|---|---|---|
| D35 | **DBOS runs under Bun**; no separate Node workers. Its system database is Postgres (there is no SQLite option); `DBOS.migrate()` runs once before workers start. | S1 passed on Bun and Node alike; parallel first launches collide on DBOS's own migrations | [S1](../../spikes/s1-s2-dbos/RESULT.md) |
| D36 | **Definition versions are workflow inputs, not DBOS versions.** A run carries its definition version and loads that snapshot in its first journaled step. DBOS's `applicationVersion` is an explicit engine label, bumped only when the engine's call sequence changes. Desktop startup moves runs left on an old engine label (fork or cancel and re-run the step, shown in the inbox); the server gets stable executor IDs and a small supervisor. | S2: DBOS pins a workflow to the version it started on and the patch API does not; the default version is a source hash that strands runs on any edit | [S2](../../spikes/s1-s2-dbos/RESULT.md), [07](07-agent-runtime.md) |
| D37 | **Desktop ships a real Postgres 18** from the per-platform `embedded-postgres` binaries, run by our own small `pg_ctl` supervisor, C.UTF-8 locale, data in `~/.memwise/postgres/data`. PGlite is the fallback only. Versions are pinned and the binaries mirrored. | S3: warm start ~140 ms on Linux, ~165 ms on macOS, ~320 ms on Windows; crash recovery and upgrades pass on all three under Node and Bun; PGlite shares one session across connections, which breaks RLS by session setting. On Windows the supervisor must poll for a real connection after `pg_ctl start` | [S3](../../spikes/s3-bundled-postgres/RESULT.md), [12](12-state-and-packaging.md) |
| D38 | **The step engine is our own loop on `pi-ai`**: every model call, policy decision and tool call is a DBOS step; pi-ai's own retries are off; idempotency keys are `workflowID:stepID`; each model attempt is recorded before it is sent; streamed text is tagged by step and attempt. | S4: a killed loop never repeated a finished call and resumed requests were byte-identical, so prompt caching holds | [S4](../../spikes/s4-pi-ai-step-loop/RESULT.md), [07](07-agent-runtime.md) |
| D39 | **One DBOS driver workflow per run**: XState's pure `transition()` over a snapshot in our tables, each step its own DBOS workflow, the transition committed in a DBOS data-source transaction guarded by a sequence number. Timers are rows with an absolute `fire_at`; outside answers go through an inbox table and name the state entry they answer. | S5 passed every crash point, including a 3-day timer across restarts | [S5](../../spikes/s5-xstate-dbos/RESULT.md), [05](05-workflows.md) |
| D40 | **Rename details:** the config folder moves once from `~/.craft-agent` to `~/.memwise` (a link is left at the old path); update checks, page sharing and session sharing are off until MemWise has its own services (opt-in env flags remain); the Craft-hosted OAuth relay and docs links stay for now and are replaced by our relay in Phase 5. Stable internal identifiers (the credentials key salts, the `craft-pages/v1` page protocol, `craft-` localStorage keys) are kept so existing data keeps working, and the old Electron profile is copied once. | Keep existing installs working without sending anything to Craft's release or sharing services | [17](17-build-plan.md) |

## Settled in Phase 1

Choices made while building the kernel ([18](18-kernel-interfaces.md)).

| # | Decision | Why | Docs |
|---|---|---|---|
| D41 | **An agent ends a step by calling a built-in `step.finish` tool** with an outcome, typed writes and a rationale; its schema is generated from the step's writes. Prose checkpoint rules are judged by a separate `verifier` model role that answers through a `checkpoint.verdict` tool; failures go back to the agent as repair rounds, then to a person. | Typed outputs instead of parsing text; the verifier can't be talked round by the agent's own transcript | [05](05-workflows.md), [07](07-agent-runtime.md) |
| D42 | **A lost effect result is retried only when the tool honours idempotency keys.** The ledger claims each key before the effect runs; a key left `pending` by a crash is re-run with the same key for such tools, and otherwise the call returns "unknown" and the step stops for a person. | Never repeat an effect blindly (07 §2) | [07](07-agent-runtime.md) |
| D43 | **Approval waits live inside the step**: an `approve` verdict records an approval request and the step hibernates on a DBOS message until a person decides. Platform defaults: read, draft and write allowed; outbound and irreversible need approval. | The step resumes mid-thought after the answer, even across restarts | [08](08-policy-and-control.md) |
| D44 | **Tool names are dotted** (`gst.validate_gstin`) everywhere in MemWise and mapped to `gst__validate_gstin` only at the model boundary. | Providers reject dots in tool names | [06](06-plugins-and-tools.md) |

## Settled in Phase 2

Choices made while building client intake for internal users ([19](19-phase-2-interfaces.md)).

| # | Decision | Why | Docs |
|---|---|---|---|
| D45 | **Roles are files, people are rows.** Roles live in `domain/roles.yaml` and are synced to Postgres at index; people, passwords and personal tokens live only in Postgres. Person and external steps name an `assignee` role; a workflow names an `owner` for attention items. | Roles are part of the definition and are checked with it (05 §8); people are instance data | [19 §1–2](19-phase-2-interfaces.md) |
| D46 | **RLS through one database role.** Every query made for someone runs inside `withActor`, which switches to the `memwise_app` role and sets the actor (person and roles, or step token) as transaction settings; compiled row rules and `domain_read` views read them. Restricted fields are cut off from the role by column grants and returned as null with their names listed. | The database enforces access for agents and people alike, and nothing depends on the app filtering rows (D31) | [19 §2–3](19-phase-2-interfaces.md) |
| D47 | **Entity tables are generated, additive only** (`domain.<entity>`), with `domain.<entity>.create` and `.get` bound as tools for every entity type. Onboard writes `Customer` through `domain.customer.create`. | Domain data lives in the domain, not in a connector's sandbox; columns are never dropped by a sync | [19 §3](19-phase-2-interfaces.md) |
| D48 | **Mechanical steps call their required tools in order with a declared `map`** from case fields to arguments, through the same gateway, ledger and approval path as agent steps. A person's answer travels beside the outcome event, not inside it, so the driver's replay guard is unchanged. | No model where none is needed (05 §3), with the same guarantees | [19 §4](19-phase-2-interfaces.md) |
| D49 | **Uploaded documents are read only through quarantined reading**: one model call with no tools, the text fenced as data, and only the requested fields kept and checked against their schema. Values from it, and judgements made after it, are marked tainted on the case. | Client documents are untrusted input (D21) | [19 §5](19-phase-2-interfaces.md) |
| D50 | **The map is SVG with our own layered layout while it is view only**; React Flow and ELK come with editing. | A small statechart needs no new dependencies, and the layout is a tested pure function | [05 §9](05-workflows.md) |
| D51 | **One domain per install for now**: the desktop keeps its project folder at `~/.memwise/project`, seeded from the intake example, and one kernel per process. The owner can act as another person on desktop, so one machine can play staff and manager; a server signs people in with email and password or a personal token. | Multi-domain workspaces are deliberately later (17). *Replaced by D70 in Phase 6.* | [19 §9](19-phase-2-interfaces.md) |
| D52 | **"Why was this flagged?" is answered from the step record only**, through a typed `explain.answer` call that must cite journal entries or outputs; citations that aren't in the record are dropped and an answer left without any is "not recorded". | Explanations must be grounded, not plausible (05 §11) | [19 §6](19-phase-2-interfaces.md) |

## Settled in Phase 3

Choices made while building playbooks by chat ([20](20-phase-3-interfaces.md)).

| # | Decision | Why | Docs |
|---|---|---|---|
| D53 | **The project folder is the live definition; a draft is a folder beside it.** `drafts/<id>/` holds a full copy of the domain and the target playbook, so a draft is itself a valid project; edits are recorded with before and after. Publishing copies the changed files over the live ones and refuses when a live file changed since the draft was made. | Every edit is a draft and live never changes in place (D33), with plain files that git and the CLI understand | [20 §1](20-phase-3-interfaces.md) |
| D54 | **A change draft bumps the playbook's version when it is made; a version index records every published version** (`mw.workflow_versions`, from the app, the CLI or files found on disk). | D55 | **Change control is two meta playbooks**, create-playbook and change-playbook, that run on the kernel like any other: a conversation, an automatic check, a manager's review, then publish. | Who may change a playbook and who approves it is policy and roles, not special code (11 §3) | [20 §3](20-phase-3-interfaces.md) |
| D56 | **Conversation steps** (`engine: open`) are agent steps that wait like person steps and are answered only from the chat anchored to them; the answer carries the chat as its provenance. System steps may take their outcome from a tool's result (`outcomeFrom`). | The interview is open work (D3) but still a step on the case's record | [20 §3](20-phase-3-interfaces.md) |
| D57 | **Chat edits playbooks only through `playbook_*` tools that write to drafts**, offered only in chats anchored to a conversation step. Chat edits stay pending until kept or discarded. | D58 | **A draft's example cases run out of process** through `memwise test` against throwaway databases on the same Postgres; past cases are replayed on the draft for information and don't block. | DBOS is process-wide, so the app can't host a second kernel | [20 §5](20-phase-3-interfaces.md) |
| D59 | **Corrections become example cases** in a change draft of the playbook ("Save as example", optionally with what a step should have done). | The playbook learns from mistakes through the same review as any change | [20 §5](20-phase-3-interfaces.md) |
| D60 | **`memwise push` publishes directly from a folder the person controls**, after its checks and example cases pass; the app publishes only through the review step. | Teams that review in git shouldn't review twice | [20 §7](20-phase-3-interfaces.md) |

## Settled in Phase 4

Choices made while building plugins and bindings ([22](22-phase-4-interfaces.md)).

| # | Decision | Why | Docs |
|---|---|---|---|
| D61 | **A plugin is a folder with `memwise-plugin.yaml`, installed by copying it to `plugins/<slug>/<version>/`, where it does nothing until bound.** Its tools are reached by routes the core picks: `builtin` (first-party code shipped with the app), `mcp` (a server the plugin declares, stdio or HTTP, or a connector set up in the app) and `command` (a subprocess per call). Claude plugins import into the same manifest: skills and MCP servers come in, tools are discovered from the servers and stay unclassified. | One format for first-party, imported and community code; installing can't change what runs (D9, D28) | [22 §2](22-phase-4-interfaces.md) |
| D62 | **A binding is a frozen file per plugin, `domain/bindings/<slug>.yaml`, made by the bind-plugin meta playbook** (install check, proposal, an agent classifying tools, dry run, review, freeze, identity resolution) through a binding draft. Only frozen bindings bind tools; a binding's class wins over the manifest's but may not loosen a declared one; the plugin's default policy and the binding's tightening are policy layers. | "A step can never use a tool the domain hasn't bound" (06 §4), and binding is reviewed like any change (D33) | [22 §3–4](22-phase-4-interfaces.md) |
| D63 | **Plugin workflows are referenced, not copied: indexing resolves them through the binding into domain terms** (entities, fields, roles, capability aliases), with an origin and a hash covering the binding. Changing one forks it into `workflows/`. Capabilities are tool aliases the binding points at a provider. | Plugins stay reusable across businesses (D10); swapping a vendor touches only the binding (06 §8) | [22 §3](22-phase-4-interfaces.md) |
| D64 | **Mappings are declarative and deterministic**: a fixed set of transforms, a direction, unmapped fields kept under the plugin's namespace. The domain stores identity links and its own fields; fields a plugin owns are read through the link, live. Writing back to the owner comes with linked entities in Phase 6. | No model runs when data moves (P1); links don't drift like copies (04 §5) | [22 §5](22-phase-4-interfaces.md) |
| D65 | **Identity resolution is deterministic in Phase 4**: exact keys first, then a name similarity with thresholds; confident matches link, uncertain ones go to the inbox, decisions are recorded and never asked again. A model for fuzzy matches waits until this falls short. | Testable and explainable; the inbox catches the rest | [22 §6](22-phase-4-interfaces.md) |

## Settled in Phase 5

Choices made while building external participants and the relay ([23](23-phase-5-interfaces.md)).

| # | Decision | Why | Docs |
|---|---|---|---|
| D66 | **Our own relay is a stateless forwarder the core dials out to**: a Cloudflare Worker with one Durable Object per install holding the core's WebSocket (hibernating when idle), and the same hub self-hosted under Bun. An install is named by its own Ed25519 key (the id is a hash of it), so the relay needs no accounts or secrets. It forwards only public routes (forms, inbox links, webhooks, the form's files), answers the OAuth callback and shared pages itself, and shows a plain "offline" page when the core isn't connected. Links are checked by the core, never the relay. | A laptop has no public address; a relay that stores nothing and can't mint access is safe to run for everyone (option 1b in the Cloudflare review) | [23 §2](23-phase-5-interfaces.md) |
| D67 | **An external link is a random token for one external step of one run, single use, expiring, revocable, stored only as a hash.** It opens the step's current waiting step run and shows only that step's fields, the comments sent back to it and its note; opening never uses it, the accepted submission does, and every other open link of the step closes. Drafts are kept on the link. What a participant types has provenance `external` and is always tainted. The same table carries person-scoped inbox links. | A client is not a user (10 §5); mail scanners open links; client input is untrusted (D21) | [23 §3–4](23-phase-5-interfaces.md) |
| D68 | **Extraction in the form is a component action**: an external or person step names one `read` tool under `extract:`, which its form may call while the step waits, through the gateway under a component token, journaled on the step run. Each value comes with a confidence that is capped unless the value is found in the document's text; only confident, found values are pre-filled, with a "from <document>" badge. A value kept as suggested keeps the tool's provenance (document, confidence, who confirmed it). | Field-level trust without letting a model's guess pass as the client's answer | [23 §5](23-phase-5-interfaces.md) |
| D69 | **Sending a link is a system step calling `external.invite`, an `outbound` effect that needs approval by default**, delivered through channel tools with fixed names (`email.send`, `whatsapp.send`) that plugins provide (SMTP, WhatsApp Cloud API); messages are fixed templates with the exact text in the preview. People may opt in to get their inbox items by email or WhatsApp, with a single-use link that decides that one item; these kernel notifications to signed-up people need no approval. Webhooks are verified per hook and recorded; acting on them is Phase 6. | Outgoing messages stay previewed and approved (D43) and swappable by binding (06 §8) | [23 §6–7](23-phase-5-interfaces.md) |

| # | Decision | Why | Docs |
|---|---|---|---|
| D70 | **A workspace is the organisation; a domain is an area of work, and a workspace holds several.** Roles are defined in the workspace and granted per domain, optionally scoped to some records. Plugins are installed once in the workspace and bound per domain or workflow. Policy layers become workspace → plugin → domain → workflow → step, still tighten only. Replaces D51. | Real organisations run several areas of work with the same people, plugins and records | [21 §1](21-domains-and-records.md) |
| D71 | **Entities in different domains are linked, not merged.** A `links:` entry names a match key and the fields it follows; each shared field has one source, is read through the link and is read-only on the other side. Matching reuses Phase 4 identity resolution, with uncertain matches going to a person. | Each domain keeps its own model (D10) without copies drifting apart | [21 §2](21-domains-and-records.md) |
| D72 | **Typed tables named by domain** (`domain.<domain>__<entity>`) in one schema: no schema per domain and no generic JSON table. The table count on hosted is handled by hosting. | Indexes, constraints, fast rollups and per-field grants need typed columns | [21 §3](21-domains-and-records.md) |
| D73 | **Record pages are generated, never stored.** An entity's `page:` section picks a layout (single, split or sidebar) and places blocks from a fixed set into named areas; without it a default is used. The details block always shows every field the viewer may see. Shared views and layouts are files; notes and personal views are rows. Row formulas and rollups compile to SQL. | Fewer hand-built pages: a well-defined entity gives its own page, and pages can't drift from the model | [21 §4](21-domains-and-records.md) |
| D74 | **Entity lifecycles are statecharts with named transitions** that say who may make them, their guards and the event they announce. Status changes only through a transition, via the gateway. Workflows declare what starts them; entities never name workflows. Invariants only flag; states can have timers. | Business events must be governed and auditable like any other write | [21 §5](21-domains-and-records.md) |
| D75 | **Four handoffs between workflows:** start, call, for each and wait until (the preferred one). A child keeps its own policy and the version it started on; checks verify inputs, outputs and call loops. | Long processes are made of smaller ones, and waiting on a condition beats polling | [21 §6](21-domains-and-records.md) |
| D76 | **`starts_on:` triggers:** entity events, dates on records, schedules and incoming messages (one address per domain, with a router workflow). Each start happens exactly once, missed runs are caught up once, bulk starts above a limit wait for approval, and triggered cases run as the workflow's owner role. | Most work starts from something happening, not a button | [21 §7](21-domains-and-records.md) |
| D77 | **Regulated mode per domain** (21 CFR Part 11, Annex 11): signed person steps with re-authentication and a hash of what was signed, and agents never sign. Record versions are hash-chained, with a reason, and can't be changed. Timestamps come from the server only. Also audit export, retention, no "act as another person", and a validation pack. Version history and server timestamps apply to every domain. | Regulated customers can't adopt the product without it, and other domains shouldn't pay for it | [21 §8](21-domains-and-records.md) |
| D78 | **Review screens are chosen by what a step writes:** document review (the Document's page in review mode, with highlights located from quoted text, not model coordinates), table review, diff review and an inbox queue mode. | Reviewing a document or a table in a form is slow and error-prone | [21 §9](21-domains-and-records.md) |

## Settled in Stage 2 of projects and pages

Settled while building pages ([26 §4, §6, §11 Stage 2](26-projects-and-pages.md)). Stage 2 uses D99–D103.

| # | Decision | Why | Docs |
|---|---|---|---|
| D99 | **A refresh's answer change is held, not applied.** The rewritten body waits in `mw.page_changes` until someone accepts it (it then becomes a new version); sent back, the page keeps its body. A refresh that finds nothing material is kept as a `nothing_new` row, which is the history's "nothing new". Versions are append-only, so Undo writes the previous body as a new version. | Nobody sees an unreviewed answer, the history can say every refresh happened, and nothing is lost by Undo | [26 §4](26-projects-and-pages.md) |
| D100 | **Keep is a schedule on the page, swept by the kernel.** The page's `refresh` holds `every`, `next`, `last`, `until` and the playbook; the minute sweep starts each due refresh once (run ids derived from the page and the slot, a closed desktop catching up once), and a kept sub-page's change marks its parent's summary due. The playbook is the app's own (`pages.refresh` in domain.yaml) or the built-in "Refresh a page". | One trigger per page would mean a trigger row per page; this keeps schedules with the page and lets an app search its own sources first | [26 §4](26-projects-and-pages.md) |
| D101 | **Answer changes go to whoever kept the page, or the app's `pages.reviewer` role.** The review step names no assignee; the kernel routes it, and the waiting list shows the item only to them, with the page's title, what was found ("1 new trial") and where it came from ("From the page's Monday refresh"). `memwise check` lets the built-in and any domain's `pages.refresh` playbook leave out the assignee. | The person who kept a page owns its answer; a role fixed in a built-in would not exist in every app | [26 §4](26-projects-and-pages.md) |
| D102 | **Page blocks: written ones are frozen, live ones are computed for each viewer.** `chart`, `tiles` and `table` are written into the body (a table cell may carry the quote it came from); `records` (a live query) and `subpages` (the sub-pages and what changed this week) are filled in on the server each time the page opens, with the viewer's access. One renderer in `@memwise/ui` draws them in pages and in chat; in chat a live block says it shows on the page. | A page's numbers must keep their source; lists of records and sub-pages must never go stale | [26 §4](26-projects-and-pages.md) |
| D103 | **A page's chat writes the page as the person, without a prompt, but only that page.** `page_get`, `page_update` and `page_create` act as the person in the chat; a write is allowed on the page the chat is anchored to and on pages it made (`chat_id`), each one a new version `via: chat:<id>` with Undo, refused in a regulated app (Stage 5 makes it a change request). Page chats also get `record_get` and `record_query`. The project ask makes a draft page; `record_update` is no longer how an asked question is answered. | The page is the answer; Undo, not a permission prompt, is the safety net for edits a person asked for | [26 §4](26-projects-and-pages.md) |

## Stage 6: EDC and studies across apps

Settled while building Stage 6 of [26](26-projects-and-pages.md) (EDC over Medidata Rave, a study across apps). D110 departs from D71 and 26 §9 on purpose and can be reversed.

| # | Decision | Why | Docs |
|---|---|---|---|
| D110 | **Rave facts are a read-only copy, refreshed on a schedule: a deliberate deviation from "read through, never copied" (D71, 26 §9).** A binding with `sync: { every }` reads its record sources again on the kernel's minute sweep and refreshes only the fields its plugin owns. The source is shown with "as of" its last read (`mw.source_syncs`), and no person or step can edit those fields. Bindings without `sync:` read through as before. The first read waits for the first index; a failed read is recorded (whatever failed) and retried within five minutes. With `sync:`, its fields are refused on create too, except the identity keys; a record the connector hasn't linked shows them as "not yet in" it. *To reverse:* drop `sync:` and the fields are read through again. Triggers then need another way to see Rave's changes, such as polling the source. | A playbook can only start from a change MemWise sees: a new coordinator in Rave has to become an entity event here. Reading through on every open gives no event. | [26 §11](26-projects-and-pages.md) |
| D111 | **The Rave connector is a first-party plugin whose tools run on builtin routes (`rave.rws.*`), every one `read`, settings from the connection.** `RAVE_URL`, `RAVE_USER` and `RAVE_PASSWORD` are declared secrets: the gateway injects them (the host serves them from its settings, only to builtins that declare them) and redacts them from results and errors. `RAVE_URL` must be https except to loopback. `RAVE_STUDY` is a setting, not a secret, since the study OID is in every reference. None comes from tool arguments. The client sends only GET. | Credentials are set once for the workspace and never re-entered or shown to a model. Data entry stays in Rave. Same pattern as SMTP (Phase 5). | [26 §11](26-projects-and-pages.md), `examples/plugins/medidata-rave` |
| D112 | **A binding field can turn another record source's outside id into the linked domain record (`transform: [{ link: <source> }]`).** Sources resolve in the binding's order, so sites come before the subjects and queries that point at them. | A subject's or query's site is a `Ref`, filled without a model or a second key match. | `examples/etmf/domain/bindings/memwise__medidata-rave.yaml` |
| D113 | **A change to a followed field is announced on the record that follows it.** It is a `changed` event with `via: link`, once per cause, so `starts_on: changed` in one app starts from a change in the app that owns the field. | eTMF asks a new coordinator for their CV when EDC (Rave) names them, with no polling in eTMF. | [26 §9](26-projects-and-pages.md) |
| D114 | **EDC is built inside the eTMF example workspace (`examples/etmf/domains/edc`).** Until Stage 3's `project.yaml` `study:`, a study is found by its key in each app's Study record. "Also in other apps" and a record's facts in other apps come from D71's link pairs. | A study across apps needs both apps in one workspace. The `edc` domain and eTMF's link to its sites already existed. | [26 §11](26-projects-and-pages.md) |
