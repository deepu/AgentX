# 19 · Phase 2 interfaces

The boundaries Phase 2 ([17](17-build-plan.md), "Client intake, internal users") is built against, in the same spirit as [18](18-kernel-interfaces.md): agreed first, built in parallel, joined at the end. Phase 1 contracts still hold and change only additively.

| App API channels | `packages/shared/src/protocol/channels.ts` (`memwise` namespace) |

**Vocabulary.** Domain experts read "playbook" for a workflow, "case" for a case, "step" for a step. UI text says playbook; code, files and these docs keep `workflow`.

## 1. Definitions (additive)

```yaml
# domain/roles.yaml (new)
roles:
  staff:   { title: Staff, description: Runs intakes and fills forms for clients }
  manager: { title: Manager, description: Approves onboarding }
  finance: { title: Finance, description: Sees bank details }
```

```yaml
# workflow.yaml: optional owner and per-state assignee
owner: manager                      # attention items (stopped runs, needs_person) go here
steps:
  needs_person: { on: { resolved: check }, assignee: manager, wait: { timeout: 7d → end } }
```

```markdown
---  # steps/verify.md
performer: person
assignee: manager                   # role that does (or decides) a person/external step
---
---  # steps/onboard.md
performer: system
tools: { allowed: [domain.customer.create], required: [domain.customer.create] }
map:                                # system steps: arguments for each tool, in call order
  domain.customer.create:
    name:  case.client_name         # `case.<field>` reads the case; anything else is a literal
    email: case.client_email
    gstin: case.gstin
    pan:   case.pan
writes:
  customer: { type: Ref<Customer>, from: { tool: domain.customer.create, field: id } }
outcomes: [done]
---
```

- `StepDef.assignee?: string`, `StepDef.map?: Record<tool, Record<arg, ArgSource>>` with `ArgSource = { case: string } | { value: unknown }`.
- `StateDef.assignee?: string`; `WorkflowDef.owner?: string`.
- `ProjectDefs.roles: Record<string, RoleDef>`, `RoleDef = { id, title, description? }`; `CheckEnvironment.roles` is filled from it, so "approval steps reference roles that exist" (05 §8) is checked.
- `PolicyDoc.approvals?: { by?: string[] }`: roles that may decide effect approvals; compiled tighten-only (intersection) into `EffectivePolicy.approvers?: Sourced<string[]>`. Absent everywhere: the step's assignee role, else the workflow owner, else any signed-in person.
- New checks: a person or external step has an `assignee` that exists; a system step maps every required argument of every tool it calls; `map` sources name case fields the step reads.

## 2. People, roles and actors (D32)

- **People and roles live in Postgres** (`mw.people`, `mw.roles`, `mw.person_roles`). Roles are synced from `domain/roles.yaml` at index; people are created in the app (desktop: the owner on first start, plus anyone they add) or with `memwise people add`.
- **Sign-in.** Server mode: `mw.auth_tokens` (personal tokens, stored as sha256) and passwords (scrypt in `mw.people.password_hash`) replace the single shared `MEMWISE_SERVER_TOKEN` for people; the shared token stays as the machine/admin credential. Desktop: the local owner is signed in; the owner may **act as** another person, so one machine can play staff and manager.
- **Actors.** Everything the kernel does for someone runs under an actor:

```ts
type Actor =
  | { kind: 'person'; personId: string; roles: string[] }
  | { kind: 'step'; token: StepToken }          // an agent or system step
  | { kind: 'system' };                         // the kernel itself (migrations, the driver)
withActor(pool, actor, (db) => …)               // @memwise/db
```

`withActor` opens a transaction, `set local role memwise_app` and sets `mw.actor_kind`, `mw.person`, `mw.roles` (comma list) and `mw.step_token` (JSON). Postgres RLS reads those settings, so the database governs people and agents alike; nothing relies on the app filtering rows.

## 3. Domain tables and RLS (D31)

- **Entity types become tables** in schema `domain`: `domain.<snake(entity)>` with `id text primary key` (`<prefix>_<ulid>`), one typed column per field (`jsonb` for Money, Address, lists and records), `lifecycle text`, `created_at`, `updated_at`, `created_by_step text`. Generated by `syncEntityTables(pool, entities)`: additive only (create table, add column), never drops.
- **Field-level access** (`access: [finance]`) compiles to a security-barrier view `domain_read.<entity>` that returns null for fields the actor's roles may not see; the app and agents read entities only through these views. Hidden case fields are nulled the same way in the case API (marked `hidden`).
- **Row rules compiled from definitions** (`compileRls(project) → string[]` of SQL, applied at index):
  - `mw.cases`, `mw.runs`, `mw.step_runs`: a person sees all rows (internal users, one organisation); a step token sees only its own case.
  - domain tables: people may read; a step token may insert only when its step allows a `domain.<entity>.create` tool.
- **Domain tools**: for every entity type the kernel binds `domain.<entity>.create` (effect `write`, idempotent on the key) and `domain.<entity>.get` (`read`), executed under the step's actor.

## 4. Human and system steps

- **Person and external steps** open a `waiting` step run (Phase 1) and now also record `assignee`. Answered with:

```ts
kernel.submitStep({ stepRunId, outcome, values?, comment?, by: personActor })
  → { applied, errors?: Record<field, string[]>, message? }
```

It checks the person has the assignee role, that the outcome is one of the step's, and validates `values` against the step's writes (`validateValue`); it then sends the outcome as the run's event **with the writes**, in the same transaction as the inbox row. The commit applies them with provenance `{ kind: 'person', by, stepRunId }` and stores `decided_by` and `comment` on the step run. A comment on a send-back is pushed as repair context into the next attempt of the step it returns to (`priorAttempts`).
- **System (mechanical) steps** run without a model: each `required` tool in order, arguments from `map`, through the tool gateway (policy check, effect ledger, idempotency key `${stepRunId}:${tool}`), each call a DBOS step; writes come from results by their `from: { tool, field }`; the outcome is the step's only outcome (`done` by default). A call that needs approval waits like an agent step; one denied or failing ends the step `needs_person`.
- **Reminders and timeouts.** A `remind` timer now writes a reminder (`mw.notifications`, for the assignee role) that the inbox shows; timeouts already move the run.
- **Inbox** (`kernel.inbox(actor) → InboxItem[]`): waiting person/external steps whose assignee is one of the actor's roles (`input` when the step writes fields, `decision` when it only has outcomes), pending effect approvals the actor may decide, attention items (runs stopped, or in a state with no step file such as `needs_person`) for the owner or state assignee, and unread reminders.
- **Approvals.** `decideApproval` gains `by: Actor` and refuses a person without an approver role (`status: 'forbidden'`).

## 5. Trust boundary: uploads and quarantined reading (D21)

- **Uploads** go to the object store (desktop: `~/.memwise/files/<sha256>`), recorded in `mw.files`; a `Document` value is `{ id, name, mime, size, sha256 }`.
- **Quarantined reading**: `quarantinedRead({ models, role: 'extractor', file, fields })` sends the document's text to the `extractor` model role with **no tools**, as data inside a fenced block, and accepts only a JSON object matching the requested fields' schema. Nothing it returns is an instruction. `intake.extract_fields` is reimplemented on it (the stub results stay for tests and example cases). Its tool results carry `tainted: true`, the session becomes tainted (Phase 1), and values written from them are marked tainted on the case.
- Taint stays **on by default**; outbound from a tainted session needs approval (platform default).

## 6. Explain: chat on a step (D3, D27)

```ts
kernel.explain({ stepRunId, question, by }) → Explanation
```

Runs the `explainer` model role (falls back to the step's own role) with the step record as its only context: the assembled context, the journal (model and tool calls, policy decisions, checkpoint), outputs with provenance and the rationale. The answer must cite journal keys or fields; a claim it can't ground is answered "not recorded". Explanations are stored in `mw.explanations`. The regular chat screen can also be opened **anchored** to a case or step (`mw.chat_anchors`); its first turn carries the same step-record digest as hidden context.

## 7. Budgets and rate limits (deferred from Phase 1)

- **Rate limits** (`tools.rules.<tool>.rateLimit`): counted per tool per domain in `mw.rate_events`, checked in the gateway's policy step before the call (journaled, so a replay takes the same decision). Over the limit: the call is refused with a message the agent sees, and the step may retry later or end `needs_person`.
- **Money budgets**: the model gateway prices each call from the role's `price` (`{ inputPerMTok, outputPerMTok, currency }`, or pi-ai's cost in USD); spend is checked against `budgets.money` when the currencies match, and a mismatch without a rate is a check warning ("money budget not enforced: no rate from USD to INR"). `describePolicy` drops "not enforced" for both.

## 9. Hosting the kernel in the app

- One kernel per process (DBOS is process-wide). Desktop: started by server-core inside Electron main after the window is up, on the bundled Postgres (D37) at `~/.memwise/postgres/data`, database `memwise`. Server: `MEMWISE_DATABASE_URL`. A failure to start never blocks chat; `memwise:status` explains it.
- **One domain per install for now** (multi-domain workspaces are deliberately later). The project folder is `~/.memwise/project` (override `MEMWISE_PROJECT_DIR`); on first start it is seeded from the bundled `examples/intake`. Definitions stay files (D13); the kernel indexes them at start and when they change.
- **Model roles** (`checker`, `verifier`, `extractor`, `explainer`) resolve to the default LLM connection when pi-ai can call it with an API key; otherwise agent steps stop with "connect a model" and the status says so. `MEMWISE_SCRIPTED_MODELS=1` runs the example cases' scripted turns instead (demos and the exit test).
- **The app API** is the `memwise:*` RPC namespace in `channels.ts`, handled by `server-core/src/handlers/rpc/memwise.ts`, remote-eligible (a remote workspace's server hosts its own kernel). Requests carry the client's person; the desktop maps its single client to the acting person. Changes are pushed as `memwise:changed` (`MwChange`), from the kernel's `onChange`.

## 10. Screens

Navigation gains three top-level sections, above the existing chat sessions, which stay as they are:

- **Inbox**: everything waiting on the acting person. Each item opens in place: the generated form (input), the approval card (decision: approve, or send back with a comment), the effect approval with its preview (email text), attention items with their events, reminders.
- **Cases**: a list with state and who it waits on; the case view shows fields with provenance badges (typed by a person, from a tool, the agent's judgement, from a document), a timeline of step records, the map with this case's path, and "Ask about this step" (explain) on any step record.
- **Playbooks**: the playbook view (numbered steps, who does each, instructions, what happens on each outcome, the effective policy per step), and the map in design and live modes (view only), with a "Start" button that opens the start form.
- **Acting as**: a person switcher in the sidebar footer on desktop.

The map is drawn with plain SVG and laid out by a small layered layout of our own (`components/memwise/map/layout.ts`), left to right, failure paths below, with a Mermaid export (D50). React Flow and ELK wait until the map becomes editable.

## 11. Exit test

`packages/server-core/src/memwise/__tests__/exit.test.ts` drives the app API as two people against a real Postgres with scripted models: staff start an intake, fill the form on the client's behalf (with documents), the check step runs, the manager sees the approval in the inbox and approves (and, in a second case, sends it back), onboard writes `Customer` to `domain.customer`, live counts show cases per step, and "why was this flagged?" is answered from the step record with citations. Screenshots of the screens are taken from the web UI against the same server.
